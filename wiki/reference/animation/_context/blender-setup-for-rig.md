# Animation Library Pipeline — Blender + Fusion Model Iterations

## The Problem

The robot model lives in Fusion 360 and is still being iterated. A pipeline already
exists to export it: Fusion → URDF → `urdf_to_blender_rigged.py` → `rig.blend`. Every
time the model changes, this script regenerates `rig.blend` from scratch.

The challenge is: **how do you build up a library of animations (walk, trot, wave, etc.)
over time, without losing them every time the Fusion model gets updated and the rig is
regenerated?**

---

## The Blender Features That Solve This

### Actions

An **Action** in Blender is a named data-block that holds a set of keyframes. It is the
unit of animation. Each clip — `walk_forward`, `trot`, `wave_fl` — is one Action.

Actions are independent of the scene. You switch between them in the **Action Editor**
(a mode of the Dope Sheet). All actions stored in a `.blend` file are accessible from the
dropdown, regardless of which one is currently "active" on the rig.

Critically: **Actions have a Fake User flag** (the shield icon in the Action Editor). If
enabled, Blender will not garbage-collect the Action on save even if it is not currently
assigned to any object. This is essential for a library file — without it, any action you
aren't currently previewing will disappear on the next save.

### Linked Libraries

Blender can reference data-blocks from an external `.blend` file in two ways:

- **Link**: a live reference. When the source file changes, the referencing file sees the
  update on reload. The linked data is read-only by default.
- **Append**: a one-time copy. The data becomes local and editable, but no longer tracks
  the source.

For this pipeline, **Link** is the right choice for the rig. You want `animations.blend`
to automatically pick up geometry and position changes whenever `rig.blend` is
regenerated, without touching your actions.

### Library Overrides (Blender 3.x+, current in 5.1)

When you Link a collection or object from an external file, it arrives read-only. To
animate it, you apply a **Library Override**: right-click the linked collection in the
Outliner → *Library Override → Make*. This creates a local override layer on top of the
linked data. You can now keyframe the empties and armature locally while still receiving
structural updates from the source file.

Library Overrides replaced the older Proxy system and are the correct approach in
Blender 5.1.

## The Recommended File Layout

```
rig.blend              ← auto-generated by urdf_to_blender_rigged.py
                         thrown away and regenerated freely
                         contains: mesh objects, armature, foot empties

animations.blend       ← your actual work, never touched by any script
                         links rig.blend via Library Override
                         contains: all Actions with Fake User enabled
                         walk_forward, trot, wave_fl, stand, ...
```

**Workflow when the Fusion model changes:**

1. Re-run the Fusion → URDF → Blender pipeline. `rig.blend` is regenerated.
2. Open `animations.blend`. Blender reloads the linked library automatically.
3. Updated geometry and rig positions appear. Your Actions are untouched — they are
   local data-blocks in `animations.blend` and the regeneration never touches that file.
4. Review each clip to check visual validity (see below). Adjust keyframes if needed.

---

## When Animations Stay Valid After a Model Change

Your Actions key the **foot empty positions in body-frame coordinates**. This means an
animation is valid across a model change as long as the reachable workspace of the feet
has not changed significantly.

Changes that are **safe** for existing animations:

- Mesh geometry refinements (surface detail, fillets, chamfers) with no structural change
- STL file updates that don't move the joint axes or mounting points
- Visual-only changes (appearance, materials)

Changes that **may invalidate** existing animations:

- Leg segment lengths change → the IK workspace shifts; foot targets that were reachable
  may now be out of range, or the robot's actual posture will look different even if the
  numbers are the same
- Hip mounting positions move → every clip's neutral pose is now wrong
- Joint axis orientations change → coordinates rotate; all keyframed positions are in the
  wrong frame

In practice: small corrections to an already-functional design rarely break animations.
A major redesign of the leg geometry will require re-authoring clips. The file split
described above means re-authoring is contained to `animations.blend` and is not caused
by the tooling — it is an unavoidable consequence of the geometry change itself.

---

## What Must Stay Stable for the Pipeline to Work

The pipeline's robustness rests on **object name stability**. Actions store keyframe
data as FCurve channel paths, which reference object names (e.g. `foot_empty_FL`,
`foot_empty_FR`). If `urdf_to_blender_rigged.py` renames these objects between runs,
existing actions will silently stop animating anything.

Concretely:

- The foot empty names must be identical across every regeneration of `rig.blend`.
- The armature and bone names must be identical.
- The body reference object (used to convert world → body frame in the exporter) must
  keep the same name.

Add an assertion to `urdf_to_blender_rigged.py` that explicitly sets these names as
constants rather than deriving them from URDF link names, which may change. A one-line
comment marking these as "pipeline contract names — do not change" is enough.

## Exporting Animations Over Time

Your `export_fhc.py` script (T4 in the roadmap) already handles this. From inside
`animations.blend`, the full clip library is always available via:

```python
for action in bpy.data.actions:
    # action.name  →  "walk_forward", "trot", "wave_fl", etc.
    # assign to rig, bake with visual_keying=True,
    # read foot empty FCurves, write .fhc
```

Running the script once exports every action in the file. There is no manual
"select which clips to export" step — the library and the export are the same thing.

A natural addition as the library grows: store per-action metadata as custom properties
directly on the Action (e.g. `action["period_ms"] = 600`, `action["clip_class"] = "TROT"`).
The exporter reads these instead of hard-coding them. This keeps the Blender file as the
single source of truth for both the keyframe data and the clip parameters.

## Summary

| Concern | Solution |
|---|---|
| Rig regeneration destroying animations | Separate `rig.blend` (generated) from `animations.blend` (authored); link via Library Override |
| Actions surviving file reloads | Fake User flag on every Action in `animations.blend` |
| Keeping animations valid across iterations | Minor model changes are safe; significant leg geometry changes require re-authoring — this is expected |
| Object name drift breaking channel paths | Hardcode pipeline contract names in the rig generator script |
| Exporting all clips at once | `bpy.data.actions` loop in `export_fhc.py` |
