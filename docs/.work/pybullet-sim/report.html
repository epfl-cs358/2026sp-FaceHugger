FaceHugger PyBullet Simulation

How a quadruped robot is simulated in PyBullet — the files involved, the physics setup, the gait and animation drivers, and how the simulation understands the project's servo/joint conventions and proves it agrees with the firmware.

Branch feat/pybullet-sim-interpreter Date 2026-05-26 Scope code/simulation/ Refs file:line, live source

0 Executive summary

The FaceHugger simulation is a thin, faithful PyBullet front-end over a URDF-derived kinematic model. Nothing about the robot's geometry is hand-typed: link lengths, mount points, joint axes and zero poses all flow from the Fusion 360 CAD export into generated/facehugger.urdf, and every Python consumer reads them back from there.

PyBullet is used for three things only — building the joint-name→index map, running the physics integrator, and applying position-controlled motor commands. All the interesting engineering sits around PyBullet. There are two ways to drive the robot:

Procedural gaits

A phase-clock generates foot trajectories, inverse kinematics turns them into joint angles, and those are pushed to PyBullet's position controllers. gaits.py + kinematics.py.

Clip playback

Baked animation clips (clips_all.h) are interpolated, converted through the exact servo-convention math the firmware uses, and pushed to the same controllers. pybullet_interpreter/.

The clip path is byte-for-byte identical to the ESP32 firmware's clip pipeline, and a parity test chain proves sim == exporter == firmware on every exported clip frame.

2 How the simulation talks to PyBullet

simulate.py is only an argument parser; the canonical engine-setup path is gaits._connect_and_setup. The same eight-step pattern is repeated by the standalone viewer.

2.1  Connecting & loading

# gaits.py:242p.connect(p.GUI if gui else p.DIRECT)
# gaits.py:249 — register PyBullet's bundled assets so "plane.urdf" resolves
p.setAdditionalSearchPath(pybullet_data.getDataPath())
if not float_mode:
    p.loadURDF("plane.urdf")        # no floor in --float mode

p.GUI opens an OpenGL window; p.DIRECT runs headless (CI). The robot loads with a 20 mm spawn clearance, free-floating base in normal mode:

# gaits.py:258robot_id = p.loadURDF(
    cfg.urdf_path,
    basePosition=[0, 0, cfg.body_height + 0.02],
    baseOrientation=p.getQuaternionFromEuler([0, 0, 0]),
    useFixedBase=float_mode,   # True = welded mid-air; False = subject to gravity/contact
)

2.2  Physics configuration — what each tweak buys

# gaits.py:250-254p.setGravity(0, 0, 0 if float_mode else -9.81)
p.setTimeStep(TIMESTEP)                                # 1/240 s — stable contact step
p.setPhysicsEngineParameter(numSolverIterations=150)   # stiffer multi-foot contact

Two changeDynamics calls add realism — a real chassis mass and grippy feet:

# gaits.py:274 & 281p.changeDynamics(robot_id, -1, mass=0.8)        # link -1 = base; bare URDF → realistic 0.8 kg
for name, idx in joint_map.items():
    if "link3" in name:                          # link3 child = foot
        p.changeDynamics(robot_id, idx,
            lateralFriction=1.2,                   # grip (default is 0.5 — feet slid)
            spinningFriction=0.05, restitution=0.0)
Fixed bug, documented in place: the foot link is matched on "link3", not "knee" — an earlier "knee" match never fired (URDF joints are named *_link3_joint), leaving feet at default friction and slipping.

2.3  Joint discovery & mapping

# helpers.py:175def build_joint_map(robot_id):
    out = {}
    for i in range(p.getNumJoints(robot_id)):
        info = p.getJointInfo(robot_id, i)
        out[info[1].decode()] = i   # info[1] = name (bytes), info[2] = type
    return out                       # {"fl_link1_joint": 0, "fl_link2_joint": 1, ...}

Fixed joints are skipped by comparing info[2] == p.JOINT_FIXED. The semantic role (shoulder/hip/knee) is recovered from the name — link1/2/3 — and the leg prefix is name[:2].

Why XML, not getJointInfo, for geometry: PyBullet silently shifts link frames to the COM when an inertial <origin> is non-zero, which would corrupt parent-frame origins. So joint geometry is parsed from raw URDF XML (helpers.py:65); PyBullet supplies only the index map and the physics.

2.4  Actuation — POSITION_CONTROL

# helpers.py:222p.setJointMotorControl2(
    robot_id, idx, p.POSITION_CONTROL,
    targetPosition=angle,    # radians (IK output or clip angle)
    force=force,             # 2.94 N·m — the torque ceiling → produces [STALL] flags
    maxVelocity=velocity,    # 5.0 rad/s — the servo slew limit
)

POSITION_CONTROL is PyBullet's built-in PD servo. Only force and maxVelocity are tuned; the PD gains use defaults. At load, joints are first teleported with resetJointState (no physics), then the motors are armed to hold that stance against gravity.

2.5  The step loop

# gaits.py:346 (run_stand — minimal form)while p.isConnected():
    p.stepSimulation()              # advance physics one TIMESTEP
    if on_step is not None: on_step(step)
    if gui: time.sleep(TIMESTEP)    # wall-clock pacing — GUI only; headless free-wheels

Stepping is manual (no setRealTimeSimulation). The gait loop adds, before each step, IK target computation and apply_joint_targets(...).

2.6  The --monitor readout: torque & current

# sim_monitor.py:68 & 24{name: p.getJointState(robot_id, idx)[3] for name, idx in joint_map.items()}
# getJointState → (position, velocity, reactionForces, appliedJointMotorTorque); [3] = torque

def estimate_current_a(torque_nm):
    return abs(torque_nm) * (2.5 / 2.94)   # linear stall model ≈ 0.85 A per N·m

Field [3] is meaningful precisely because the motor runs in POSITION_CONTROL. Constants: stall torque 2.94 N·m (30 kg·cm servo), stall current 2.5 A, 10 A supply budget ([WARN >10A]), 2.5 N·m [STALL] flag. Fires every 30 steps (~8 Hz).

3 Procedural gaits & kinematics

GAITS table ──▶ gait_joint_targets(t) ──▶ foot_target(phase) (body-frame XYZ) └─▶ cfg.leg_ik ──▶ (θ_s, θ_h, θ_k) └─▶ apply_joint_targets └─▶ p.setJointMotorControl2

3.1  The URDF-derived kinematic model

The per-leg transform chain (kinematics.py:3):

T = Rz(yaw_offset + θ_s) · Ttrans(L1) · Ry(s_h) · Ttrans(L2) · Ry(s_k) · Ttrans(foot_L3)
    s_h = leg.hip_axis_sign  · θ_h
    s_k = leg.knee_axis_sign · θ_k

Shoulder θ_s yaws about body +Z; hip/knee pitch about ±Y. User-facing angles are uniform — the same numeric angle puts every leg in the same physical pose; the per-leg axis_sign carries the mirroring. All geometry is read from the URDF, never hardcoded:

# kinematics.py:324mount      = sh_joint["xyz"]
yaw_offset = sh_joint["rpy"][2]
L1_vec     = hip_joint["xyz"]
L2_vec     = knee_joint["xyz"]

Inverse kinematics decouples shoulder yaw with atan2 (the Y component in the link1 frame is invariant under both Ry rotations), then solves a planar 2-link triangle by law of cosines, clamped to a reachable range:

# kinematics.py:155 & 179 (condensed)w_y = leg.L1_vec[1] + leg.L2_vec[1] + leg.foot_L3[1]
theta_s = _wrap_pi(atan2(dy, dx) - atan2(w_y, w_x) - leg.yaw_offset)

d = min(max(hypot(u, v), abs(l2 - l3) + 1e-6), l2 + l3 - 1e-6)
cos_kprime = (d*d - l2*l2 - l3*l3) / (2*l2*l3)
kprime = acos(_clamp(cos_kprime, -1, 1))
An unreachable foot target yields the nearest reachable pose, not an error. A startup self-check (gaits.py:319) round-trips the neutral foot through leg_ik and asserts the result matches the stance within 2°.

3.2  Config is deliberately thin

# facehugger_config.yaml:95servo:
  mass_kg: 0.300
  effort_nm: 2.94        # 30 kg·cm → N·m   (→ cfg.servo_force)
  velocity_rad_s: 5.0     # (→ cfg.servo_velocity)

Link lengths/limits/axes are not here (they live in the URDF). Shoulder-rest fields were removed after "Convention A" (derived in code now). Gait params are not here — they live in the GAITS dict; stance bend lives in constants.py.

3.3  The gait engine

# gaits.py:32GAITS = {
  "walk": {"period": 2.4, "duty": 0.25,   # 3 feet always planted = static
           "offsets": {"fl": 0.00, "br": 0.25, "fr": 0.50, "bl": 0.75}},
  "trot": {"period": 0.8, "duty": 0.5,    # diagonal pairs together
           "offsets": {"fl": 0.0, "br": 0.0, "fr": 0.5, "bl": 0.5}},
}

A normalized phase clock drives each leg with its offset. The foot target is a half-sine swing arc followed by a flat ground-push stance:

# gaits.py:64 (foot_target — condensed)if phase < duty:                          # SWING (in the air)
    s = phase / duty
    d  = -step_length*0.5 + s*step_length    # back → front
    dz = step_height * sin(pi * s)         # half-sine lift
else:                                     # STANCE (push back on the ground)
    d  = step_length*0.5 - s*step_length
    dz = 0.0
return (nx, ny + d, nz + dz)             # body +Y = forward

3.4  The shoulder-rest convention

# generate_urdf.py:182 — bakes the rest into the URDF joint originsif leg_id == "fl": return fl_rest_rad                        # −45°
if leg_id == "fr": return -fl_rest_rad                       # +45°
if leg_id == "bl": return -_wrap_pi(fl_rest_rad + pi)        # −135°
if leg_id == "br": return  _wrap_pi(fl_rest_rad + pi)        # +135°

The four legs splay outward into their quadrants. These signs (BL=−wrap_pi(FL+π), BR=+wrap_pi(FL+π)) are the corrected version — a docstring records an earlier revision had BL/BR swapped, sending the back legs into the front quadrants.

4 The clip interpreter — how conventions are understood

The headline feature of this branch. Its mission: mirror the firmware clip pipeline exactly so a clip can be validated visually in sim before flashing to the ESP32.

4.1  Data flow

clips_all.h (C arrays, pre-scaled math-space degrees) │ load_clips_all_h (regex parse) ▼ list[ClipData] → frames: ClipFrame{t_ms, a[12]} │ _interpolate_frame(elapsed_ms) (linear, clamped at ends) ▼ a[12] math-space degrees │ frame_to_joint_targets — per leg (FR, FL, RR, RL): │ translate_to_servo → clamp_clip_servos → servo_to_radians │ × LEG_ID_TO_URDF_AXIS_SIGN (URDF <axis> correction, sim-only) ▼ dict[urdf_joint_name → radians] │ ClipPlayer.step ▼ pybullet.setJointMotorControl2(POSITION_CONTROL) → stepSimulation @ 240 Hz

4.2  Clip format

The loader reads animation/exported_clips/clips_all.h — a C header, not .fhc or JSON, generated by the Blender add-on. Crucially, the a[12] values are already pre-scaled math-space degrees (the exporter baked in the 2/3-scale), so only translate_to_servo runs at playback. Layout is firmware leg order: a[0..2]=FR, a[3..5]=FL, a[6..8]=RR, a[9..11]=RL, each (sh, th, kn).

4.3  servo_convention.py — the crown jewel

The single Python source of truth for math-space → servo → radian, ported line-for-line from firmware motion_math.cpp. This is how the simulation "understands" the robot's conventions. The NEUTRAL standing pose, then the core conversion:

# servo_convention.py:61 & 98NEUTRAL = [
    NeutralPose(sh=45,   th=-60, kn=-37),   # FR
    NeutralPose(sh=135,  th=-60, kn=-40),   # FL  (# Change B: 135 so "outward" matches)
    NeutralPose(sh=-45,  th=-50, kn=-50),   # RR / BR
    NeutralPose(sh=-135, th=-60, kn=-35),   # RL / BL
]

if   leg_id == LEG_FR: hip = 90 + (sh - 45);  thigh = 90 - th; knee = 90 + kn
elif leg_id == LEG_FL: hip = 90 + (sh - 135); thigh = 90 + th; knee = 90 - kn
elif leg_id == LEG_RR: hip = 90 + (sh + 45);  thigh = 90 + th; knee = 90 - kn   # BR un-mirrored
elif leg_id == LEG_RL: hip = 90 + (sh + 135); thigh = 90 - th; knee = 90 + kn

How the conventions are encoded:

  • Shoulder/yaw — 90 + (sh ± offset), the offset being that leg's rest yaw, so feeding the NEUTRAL sh yields exactly servo 90. The +sh sign is uniform across all four legs.
  • Thigh — sign alternates per diagonal pair (FR/RL −th, FL/RR +th), encoding the mirrored servo mounting of the body's two sides.
  • Knee — the opposite alternation.
The BR un-mirror (2026-05-25) — load-bearing. The original plan had RR hip = 90 − (sh + 45). The shipped code flips this to 90 + (sh + 45): the BR motor is an identical part with its yaw shaft on the same vertical axis, so +sh = +servo like every other leg. The test suite carries a verbatim copy of the new formula as ground truth, so reverting BR would fail loudly.

The final step is a pure offset+scale, clean because the URDF joint zero is defined to coincide with servo-90 neutral:

# servo_convention.py:158return math.radians(servo_deg - 90.0)   # 90→0, 0→−π/2, 180→+π/2

4.4  The URDF axis-sign correction (sim-only)

A subtlety absent from the firmware — physical motors don't care about URDF <axis> orientation, but PyBullet does. The URDF flips the axis on the diagonal pairs, so the clip player multiplies by a per-leg sign:

# servo_convention.py:38 & clip_player.py:54LEG_ID_TO_URDF_AXIS_SIGN = {LEG_FR: -1, LEG_FL: +1, LEG_RR: +1, LEG_RL: -1}

targets[f"{urdf_name}_link1_joint"] =  axis * servo_to_radians(servo.hip)
targets[f"{urdf_name}_link2_joint"] =  axis * servo_to_radians(servo.thigh)
targets[f"{urdf_name}_link3_joint"] = -axis * servo_to_radians(servo.knee)   # knee = −axis

Applied here, not in the servo math — keeping the firmware-parity math byte-identical while still rendering correctly in sim. (A stale docstring at clip_player.py:48-50 wrongly claims link1 needs no correction; the code and the lower comment are right.)

Why the URDF is the single source of truth

A hand-written kinematics.py from another branch was rejected: its hardcoded link lengths (L1=0.080, L2=0.075, L3=0.077) were built against a different CAD revision than the live export (≈0.058 / 0.095 / 0.097), and would deliver IK solutions for the wrong robot. The design generates the URDF from CAD so that moving any construction point in CAD propagates automatically; every consumer reads geometry from the URDF.

# facehugger.urdf:67 — a representative joint<!-- LEG: FL (side=L, shoulder_rest=-45.0°, limits=[-52.0°, +90.0°]) -->

6 Sim ↔ firmware parity — the guarantee

verify_export_parity.py proves the sim interprets exported clips identically to the firmware/browser, by deriving each servo command from independent paths and asserting agreement with exact integer equality:

# verify_export_parity.py:101for i, (frame, js) in enumerate(zip(clip.frames, js_frames)):
    sim = _sim_servo_js_equiv(list(frame.a))   # runs translate_to_servo per leg
    for leg in _JS_ORDER:
        if sim[leg] != js[leg]:                 # exact int after shared [0,180] clamp
            errors.append(...)

The two paths are produced by separate implementations of the translateToServo contract (the sim's servo_convention.py vs the exporter's fh_clip_panel._frame_to_servo). The firmware C++ is locked to the exporter separately by a Unity test (1° tolerance). So the full chain closes the loop:

clips_all.h → sim servo_convention ≡ .js (exporter _frame_to_servo) [exact int] exporter _frame_to_servo ≡ firmware translateToServo [1° tolerance] ──────────────────────────────────────────────────────────────────────────────────────── ∴ sim's PyBullet servo output ≡ firmware's physical servo command (every clip frame)

The sim's translate_to_servo is byte-identical to firmware motion_math.cpp:translateToServo — same per-leg formulas including the 2026-05-25 BR un-mirror. The pure-math test suites (no PyBullet) carry a verbatim firmware-formula copy as independent ground truth and validate the loader against a JSON manifest, so the convention contract is regression-locked from both ends.
