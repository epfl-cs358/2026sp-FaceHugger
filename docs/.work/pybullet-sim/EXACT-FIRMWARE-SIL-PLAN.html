Run the exact firmware code in the sim

Compile the actual flashed firmware C++ and drive the PyBullet robot with it — so a clip or gait that passes in simulation is guaranteed to issue the same servo commands on the real robot, and every firmware change is testable before flashing.

Approach software-in-the-loop (SIL) Extends GAIT-AND-PARITY-PLAN.md (Approach B) Companion EXACT-FIRMWARE-SIL-PLAN.md

1 What you want, and why it's right

Run the same C++ I flash to the ESP32 inside the sim, so testing the exported clips (and gaits, and any firmware change) proves they'll do the right thing on the robot — and flag any angle that shouldn't run.

This is software-in-the-loop (SIL): the firmware's logic runs on the host, its hardware is replaced by the simulator. It kills the one weakness of today's setup — the sim's clip interpreter is a hand-written Python re-port of the firmware, which can silently drift from the C++. SIL removes the re-port: one implementation (the firmware), exercised in both places. If the exporter emits bytes the firmware mishandles, the sim misbehaves identically — exactly the bug you want to catch before flashing.

2 Can we use the firmware code directly?

Short answer: not as an import — it's C++. The path is compile → load → call.

  1. Compile the firmware control sources into a host shared library (.dylib/.so) — the same .cpp files that build for the ESP32, for the host CPU.
  2. Load it from Python via an FFI.
  3. Call it each sim step: feed a command + a synthetic clock, read back the 12 servo angles, drive PyBullet.

The obstacle: the interesting files are hardware-coupled. Verified in the tree:

FileHardware / timing depsIn native build today?
motion_math.cppnone (#ifndef ARDUINO-clean)✅ yes
kinematics.cppnone✅ yes
spinal_cord.cpp (holds tickGait/tickClip)<Arduino.h> <Wire.h> <Adafruit_PWMServoDriver.h>, millis(), Serial❌ no
servo.cppsame + pwm.setPWM(), map()❌ no
leg.cppsame❌ no
network.cppWebSocketsServer(81), WiFi, ArduinoJson❌ no

So translateToServo (the math) already compiles on the host — but the control logic that calls it (tickGait, tickClip, the state machine) does not, because it pulls in Arduino + the PCA9685 driver + millis(). To run that exact code on the host we must satisfy those deps without changing the firmware logic.

Two ways to make the exact code compile on the host

Option A — Mock the hardware

Host Arduino.h shim (injectable millis()), empty Wire, a recording Adafruit_PWMServoDriver mock that stores each setPWM. The exact spinal_cord/servo/leg.cpp compile unmodified.
+ firmware untouched. − you maintain the mocks.

Option B — HAL seam recommend

Put the servo sink + clock behind interfaces (IServoBus::writeAngle, IClock::millis), injected at construction. ESP32 injects PCA9685+real clock; sim injects a recording sink + sim clock.
+ clean, records degrees (no PWM-truncation noise). − a one-time firmware refactor (still "the flashed code").

Recommendation: start with A to prove it (zero firmware change), land B for maintainability — the seam is tiny because the firmware already funnels every write through Servo::setServoAngle and reads time only via millis().

Why this gives you the guarantee: either way, exporter bytes → clips_all.h → the exact firmware tickClip/translateToServo → 12 servo angles → PyBullet. Sim and robot run the same code on the same data, so "passes in sim" ⇒ "issues the same commands on hardware." The current Python re-port cannot make this claim.

3 The FFI binding — Python calls the firmware

ctypes (stdlib, via an extern "C" shim) or pybind11 (binds the C++ SpinalCord class directly). pybind11 is recommended — the control core is class-based, so binding the object is natural.

# the seam the sim drives — a pybind11 wrapper over the real SpinalCord
class FirmwareControl:
    def command(self, json_str): ...   # an API_SPEC T: command (or typed call)
    def tick(self, t_ms: int): ...     # advance firmware one logical tick at sim time
    def servo_angles(self) -> list[12]  # 12 recorded servo degrees (FR,FL,RR,RL × sh,th,kn)

The sim loop becomes: per 240 Hz step, fw.tick(step*1000/240), read servo_angles(), convert to URDF radians via the existing servo_to_radians + LEG_ID_TO_URDF_AXIS_SIGN (the sim-only axis correction), and setJointMotorControl2. The servo degrees now come from the firmware, not the Python port.

4 Where it lives + how a firmware change gets tested

# a small package, sibling to pybullet_sim/
code/simulation/firmware_sil/
  hal/             host Arduino shim + recording servo bus (+ sim clock)   # Option A
                   OR the injected sim backends                            # Option B
  sim_api.cpp      extern "C" / pybind11 entry point over SpinalCord
  build.py/CMake   compile the EXACT firmware sources + hal -> fh_sim.{so,dylib}
  bridge.py        FirmwareControl wrapper + the PyBullet driver loop

The build pulls firmware sources by path from code/firmware/src/… (not copies), so there is no second copy to drift. A facehugger.py sim --firmware flag selects the SIL driver over the Python re-port.

Testing any firmware change

  • Clip validation: play every clip in the firmware's clips_all.h through the SIL; assert no servo leaves its mechanical range, and (regression) that the servo-angle sequence matches a stored golden trace. A bad exporter or a firmware edit that drives an out-of-range angle fails the test.
  • Out-of-range flagging: the SIL records the pre-clamp requested angle, so the sim can flag "servo X commanded to 195° (clamped)" — surfacing bugs the robot would silently swallow.
  • Gait / changes: same harness, pinned (gait, X/Y/Yaw, t) inputs.

5 Simulating the JS app + the WebSocket entrypoint

The robot's control surface is a WebSocket server on port 81 speaking the T:-tagged JSON protocol (code/API_SPEC.md). Stand up that same entrypoint in front of the SIL core.

React-Native / Expo app (unmodified) ← the real JS, unchanged │ ws://localhost:81 (API_SPEC T: commands) ▼ sim WebSocket server ──► FirmwareControl.command() ──► exact firmware dispatch │ │ │ tick(t) → servo_angles() ▼ ▼ telemetry/state back to app PyBullet robot moves

Two fidelity levels for the command-handling layer:

  • (i) Python WS shim recommend first — a Python websockets server on :81 parses the T: JSON and calls FirmwareControl.command(...). Motion code is exact; only the transport+parse glue is Python. The app can't tell it's a sim.
  • (ii) Exact network handler — compile network.cpp's dispatch into the host core too. Maximal fidelity, but the links2004 WebSockets lib is ESP-oriented and awkward on host — so extract/compile the JSON→command dispatch, leave the socket transport to Python.

For the JS itself: run the Expo app (or a headless Playwright run of the web build) pointed at ws://localhost:81. The JS runs unmodified and drives the simulated robot end-to-end — validating app → protocol → firmware command handling → motion, on the desktop, before touching hardware. It also becomes a regression test for API_SPEC.md drift.

6 Mass & physical tuning (the not-guaranteed part)

SIL guarantees the commands match. It does not make the robot move like reality — that's the physics model. Tune it against measurements:

6.1 Mass budget

  • Per-servo mass: config has mass_kg: 0.300 as an unverified placeholder — weigh one QYRC DSS-230MG and set it.
  • Per-link inertials: prefer CAD density-based mass per body where the Fusion physics export is incomplete (audit generate_urdf.py's inertial path).
  • Chassis/electronics: the 0.8 kg BODY_MASS_KG is an estimate — weigh the assembled chassis; the battery position drives the CoM, which dominates balance.

6.2 Servo dynamics

PyBullet's POSITION_CONTROL is a PD model capped by force/maxVelocity. Use the --log torque/current trace as the instrument: run a known motion on the real robot, run it in sim, tune force/maxVelocity/positionGain until the traces match.

6.3 Friction / contact

Tune lateralFriction / spinningFriction against observed foot-slip (a push test calibrates lateral friction).

6.4 Protocol

Pick 2–3 reference motions → measure on hardware (angles, current, IMU/video) → run identical in sim with --log → tune mass → friction → servo gains (mass dominates) → lock config → re-run the SIL clip suite to confirm commands unchanged.

7 How strong is the guarantee? (two tiers)

Command fidelity — GUARANTEED

SIL runs the exact firmware tickClip/tickGait/translateToServo on the exact data. The 12 servo angles are identical to the robot's by construction. The per-tick smoothers (clip EMA, input *0.1) are loop-rate dependent — but SIL runs the real smoother code, so matching the firmware's tick cadence matches them exactly; uint16_t degree quantisation is reproduced (it's the real code). A clip that passes SIL issues the same commands on the robot.

Physical fidelity — APPROXIMATE

Whether the robot balances / slips / tips the same is a tuning problem (§6), never exact. SIL + good mass/friction tuning gets "plausible, catches gross failures (falls, collisions, out-of-range)", not "physically certified."

On the tin: "If it commands correctly in sim, it commands correctly on the robot (guaranteed). Whether it moves the same is tuned, not guaranteed." For validating your exporter, the guaranteed tier is exactly what you need.

8 Build / CI integration; risks

Build: a native-style target (PlatformIO env:native exists, or a standalone CMake) compiles firmware sources + HAL/mock + sim_api into fh_sim.{so,dylib}. CI builds it once and runs the SIL clip suite. Keep the Python re-port as the no-C++-toolchain fallback.

Honest caveats

  • float determinism: host double == ESP32 soft-float double for IEEE-754 ops — safe.
  • third-party libs on host: Adafruit_PWMServoDriver / WebSocketsServer are Arduino-oriented — mock them (A) or seam them out (B); don't build them on host.
  • millis() must be injected/synthetic for determinism — never the wall clock.
  • two clips_all.h copies already drift by hand; the SIL clip suite should read the firmware copy, so it tests what the robot will actually run.

10 Suggested sequencing (when approved)

  1. Proof of concept (Option A, clips): Arduino shim + recording PCA9685 mock; compile spinal_cord.cpp + deps natively; extern "C" tick/read_servos; ctypes; play one clip through PyBullet via SIL. Confirms the exact code runs.
  2. SIL clip suite: drive all clips from the firmware clips_all.h; golden-trace + out-of-range assertions; CI. This validates your exporter.
  3. Gait via SIL: feed (gait, X/Y/Yaw) commands; same harness.
  4. HAL seam (Option B) + pybind11: retire the mock for a clean injected seam.
  5. WebSocket entrypoint: Python WS server on :81 → FirmwareControl.command; point the Expo app at it; full-stack SIL.
  6. Mass/physics tuning (§6): calibrate against real measurements; lock config.
Each step is independently useful; step 2 already delivers the headline goal — test the exported clips in sim and know they'll run correctly on the robot.
